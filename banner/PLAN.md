# Build `@guchho/banner` — A Production-Ready Guchho Plugin

## 1. Objective

Create a standalone, production-ready npm package named **`@guchho/banner`** for injecting copyright, package metadata, and license banners into JavaScript and CSS build outputs generated by Guchho.

The package must be reusable across multiple projects, easy to configure, deterministic by default, compatible with Guchho's existing plugin API, and ready for npm publication.

**GitHub repository name:** `guchho-banner`

**npm package name:** `@guchho/banner`

The plugin must support both JavaScript and CSS output. Neither language is optional.

Before implementation, inspect the actual Guchho repository, plugin API, lifecycle hooks, output pipeline, minifiers, source-map implementation, and existing banner functionality. Use only verified APIs and capabilities.

Do not invent plugin hooks, assume unsupported behavior, or perform unrelated refactoring.

## 2. Required Public API

The plugin must expose a default export named `banner`.

Required usage:

```js
import banner from "@guchho/banner";

export default {
  plugins: [
    banner({
      style: "long",
      packageJson: "./package.json",
    }),
  ],
};
```

This configuration must work with Guchho's actual plugin system.

The same configuration must apply the generated banner to eligible JavaScript and CSS outputs automatically. Users should not need separate JavaScript and CSS plugin instances.

Keep the API simple, predictable, and suitable for production projects.

## 3. Configuration Options

Implement the following options:

| Option        | Type                | Default               | Purpose                  |
| ------------- | ------------------- | --------------------- | ------------------------ |
| `style`       | `"short" \| "long"` | `"long"`              | Banner formatting        |
| `packageJson` | `string`            | `"./package.json"`    | Package metadata file    |
| `date`        | `boolean`           | `false`               | Include the build date   |
| `year`        | `number \| string`  | Current year          | Copyright year           |
| `name`        | `string`            | From package metadata | Override package name    |
| `version`     | `string`            | From package metadata | Override package version |
| `author`      | `string`            | From package metadata | Override author          |
| `license`     | `string`            | From package metadata | Override license         |

Requirements:

* Validate `style` and reject unsupported values with a clear error.
* Explicit overrides must take precedence over `package.json`.
* Resolve the metadata file relative to the appropriate project or configuration directory supported by Guchho.
* Do not bind project metadata to the plugin's installation directory.
* Avoid reading the metadata file repeatedly for every output file.
* Do not emit `"undefined"`, `"null"`, or malformed metadata in the banner.
* Handle missing optional fields with documented, predictable behavior.
* Support npm-style `author` objects as well as author strings when practical.
* Set `date` to `false` by default for reproducible builds.
* When `date: true`, include a consistently formatted date and document its effect on deterministic output.
* Keep the option surface minimal. Do not introduce unnecessary aliases or complex configuration layers.

If an option's behavior depends on Guchho's actual API, verify the capability and document any limitation rather than pretending it works.

## 4. Banner Formatting

Support two styles: `short` and `long`.

### Short format

Example:

```js
/*! truehuman v0.0.6 | Copyright (c) 2026 Hemanta Gayen and contributors | GPL-3.0 License */
```

### Long format

Example:

```js
/*!
 * truehuman v0.0.6
 * Copyright (c) 2026 Hemanta Gayen and contributors
 *
 * Released under the GPL-3.0 License
 */
```

These are illustrative examples, not hardcoded values.

Generate the banner from the configured options and project metadata.

Formatting requirements:

* Use a consistent, professional style.
* Use valid comment syntax for JavaScript and CSS.
* Prevent malformed comments when metadata contains newlines or comment terminators.
* Avoid duplicated copyright text, empty metadata fields, and awkward blank lines.
* Ensure identical inputs produce identical output.
* Do not imply that a license identifier alone contains the complete license text.
* Do not add a trailing build date unless `date: true`.

## 5. Mandatory JavaScript Support

Inject the generated banner at the beginning of eligible JavaScript build outputs.

Support all JavaScript output formats that the actual Guchho build pipeline supports, including ESM, CJS, IIFE, UMD, and other supported formats where applicable.

Requirements:

* Work with both minified and unminified JavaScript.
* Preserve the banner during minification.
* Prefer the legal-comment form `/*! ... */` when compatible with Guchho's comment-preservation behavior.
* Do not disable minification to preserve the banner.
* Do not change Guchho's global minification defaults.
* Preserve JavaScript semantics, module directives, and generated runtime helpers.
* Do not break `"use strict"` or other directive prologues.
* Preserve source-map correctness.
* Avoid duplicate banner injection.
* Respect the existing built-in banner configuration.
* Do not alter unrelated JavaScript comments.

Verify the actual minifier behavior. Do not assume that a legal-comment marker is automatically preserved.

## 6. Mandatory CSS Support

Inject the generated banner at the beginning of eligible CSS build outputs.

JavaScript support alone does not satisfy this task.

Requirements:

* Support both minified and unminified CSS.
* Use valid CSS block-comment syntax.
* Preserve the banner after CSS minification.
* Do not disable CSS minification to preserve the banner.
* Do not change CSS selectors, declarations, at-rules, imports, or stylesheet semantics.
* Preserve CSS source-map correctness.
* Avoid duplicate banner injection.
* Apply the same metadata and formatting options used for JavaScript.
* Respect the existing built-in banner configuration.

Example CSS output:

```css

```

The generated banner must be valid for both JavaScript and CSS. Since both formats support block comments, use one shared banner representation where appropriate, without introducing format-specific syntax that breaks either language.

## 7. Shared JavaScript and CSS Behavior

Use a single plugin instance:

```js
import banner from "@guchho/banner";

export default {
  plugins: [
    banner({
      style: "long",
      packageJson: "./package.json",
    }),
  ],
};
```

That instance must handle all eligible JavaScript and CSS outputs.

Requirements:

1. Resolve metadata once when appropriate.
2. Generate the banner consistently across output files.
3. Apply it to eligible JavaScript and CSS files.
4. Support multiple entry points and multiple output files.
5. Work with multiple build configurations without leaking state between unrelated projects.
6. Prevent repeated injection into the same output.
7. Preserve output ordering and build pipeline semantics.
8. Avoid unnecessary parsing or copying of large output files.
9. Respect built-in Guchho banner settings.
10. Preserve existing error reporting and logging conventions.

Define a predictable interaction between the plugin banner and Guchho's built-in banner. Do not silently overwrite either banner or unexpectedly duplicate the same content.

Do not inject banners into HTML, JSON, source maps, binary assets, images, fonts, or unrelated output types.

Determine eligibility using the actual output metadata and build pipeline rather than relying only on filenames when the API provides a more reliable signal.

## 8. Plugin API and Build Pipeline Integration

Inspect the real Guchho plugin API before choosing the implementation.

## 9. Source-Map Requirements

Source-map correctness is mandatory for JavaScript and CSS when source maps are enabled.

Requirements:

* Support the source-map modes actually implemented by Guchho.
* Ensure the inserted banner does not cause generated mappings to point to incorrect original locations.
* Update mappings or use a supported pipeline mechanism that preserves correctness.
* Preserve `sources`, `sourcesContent`, and other existing map information where applicable.
* Avoid stale mappings and incorrect generated line offsets.
* Test external and inline source-map modes if Guchho supports them.
* Verify that the final map corresponds to the final emitted output.

Do not merely assert that a `.map` file exists. Verify mappings and generated positions using the project's existing test utilities or a suitable source-map consumer.

If a particular source-map mode cannot be supported by the existing API, report the limitation explicitly and do not claim complete support.

## 10. Minification and Legal Comments

The plugin banner must survive both JavaScript and CSS minification.

Requirements:

* Verify the actual behavior of both minifiers.
* Preserve this plugin's legal banner without globally preserving every comment.
* Do not disable minification.
* Do not change default minification behavior.
* Do not modify unrelated comment handling.
* Ensure short and long styles both survive minification.
* Test output with the exact Guchho production build pipeline.

If the existing minifier strips legal comments, use the smallest supported mechanism to preserve the plugin banner. If a minimal core change is required, keep it scoped and backward-compatible.

## 11. Metadata Resolution and Error Handling

Implement robust metadata loading.

Requirements:

* Resolve `packageJson` against the project/configuration directory supported by Guchho.
* Handle nonexistent files, invalid JSON, unreadable files, and invalid option values.
* Provide concise, actionable errors.
* Preserve useful context, such as the resolved file path.
* Do not silently fall back when the configuration is invalid.
* Do not emit malformed banner output when metadata is missing.
* Do not read the package metadata at module-import time if that binds it to the wrong project.
* Avoid caching metadata globally across unrelated build configurations.
* Ensure explicit overrides are applied after metadata loading.
* Document how the plugin handles missing name, version, author, and license values.

Do not introduce a large hierarchy of custom error classes for simple configuration errors.
